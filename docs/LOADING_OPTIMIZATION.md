# 0.8.5：移植 Slop New York 的小体积地图加载方式

日期：2026-11-01。运行系统继续基于台北版；这是一次针对数据传输与启动的选择性移植。

## 上游更新与移植范围

本地 `../reference-slop-newyork` 从 `819a0ad` 快进到 `e35c06c0d896052a80ff117aefe8b99e978913d4`，对应本轮从 GitHub 拉取的最新 main。参考仓库工作区干净。

直接参考的上游实现：

- `062c4a9`：独立 gzip 建筑资产，元数据、X/Z 流分离，zigzag/varint 坐标编码。
- `7249a39`：树木数据采用相同独立压缩资产方式。
- `2813f08`：根据 gzip 魔数判断是否还需要解压，兼容服务器已经通过 Content-Encoding 自动解压的情况。
- `js/main.js` 的 `showLoadingStage`：隐藏标签页不等待 rAF；前台标签页的绘制让步有超时后备。

上游纽约的 NYB1 格式只包含其建筑字段，不能直接塞入武汉的道路、坡道、桥隧、历史立面和来源字段。本次保留其打包与加载策略，扩展为适配武汉结构的 WUH1。没有直接覆盖台北控制器，也没有引入纽约地理数据或整批更新材质、车辆、树木系统。完整来源版本记录在 `UPSTREAM.json`；代码沿用 MIT 许可归属，地理数据库归属不变。

## 旧版问题

`js/runtime/wuhan-geodata.js` 原先直接导出完整城市对象，文本约51.81 MB。它把运行数据、重复的建筑轮廓和大量生成审计字段一起送进 JavaScript 构建器。旧生产主包约49.64 MB，gzip后仍约8.17 MB；浏览器还需要把这部分地图当作JavaScript解析。

不能用51.81 MB与4.34 MB直接宣称网络减少九成：旧页面服务器也可能压缩JavaScript。下表把文件文本、压缩包和实际传输分开。

## 当前结构

1. `tools/build-runtime.py` 继续从固定 `public/data/city.json` 生成同一份武汉场景数据。
2. `tools/runtime_package.py` 生成 `js/runtime/wuhan-geodata.bin.gz`，`wuhan-geodata.js` 变成很小的异步加载入口。
3. WUH1共享字符串表；整数和交错坐标使用varint；只有能精确还原的数字才采用毫米定点编码，其余保留Float64。**不简化多边形，不改变楼高，不压缩城市距离。**
4. 用于街具避让的 `placementData` 只发送运行中需要的建筑原始轮廓、道路字段等。没有改用精度更低的渲染轮廓；完整来源、用途、高度证据等仍在 `public/data/city.json` 和审计文件中。渲染建筑所需的元数据和来源标识继续提供。
5. 浏览器请求独立资产，自动识别是否已被服务器解压；解包失败或HTTP错误会显示原因和重试按钮。
6. 数据请求过程中显示读取状态；服务器自动解压时不把解压后的字节量冒充网络下载量。场景构建仍用不定进度，着色器阶段继续使用实际任务进度。
7. 前台阶段先让标签绘制，后台标签页也能继续启动，不会卡死在等候rAF上。

静态部署时，Vite把资产输出为带内容哈希的独立 `.gz` 文件，使用相对URL，适用于项目子路径。Node数据测试通过同一加载入口读取本地文件，复用同一解码器。

## 体积与浏览器结果

MB均为十进制字节，不是MiB。精确值见 [metrics.json](acceptance/loading-0.8.5/metrics.json)。

| 项目 | 修改前 | 修改后 |
|---|---:|---:|
| 地图导出JavaScript文本 | 51.81 MB | 小型加载入口，约0.23 KB |
| 地图数据按gzip压缩 | 7.84 MB | 4.34 MB，约减少44.7% |
| 解包后WUH1字节 | 无 | 8.71 MB，仍需解码成运行对象 |
| 生产主JavaScript文件 | 49.64 MB | 1.30 MB |
| 首次资源正文实测（含HTML、脚本、样式、地图） | 本轮未重跑旧版浏览器冷启动 | 约4.98 MB，本机预览、HTTP压缩、冷缓存 |

实测有两种托管响应：本机Vite预览自动解压时，fetch读取8.71 MB，但资源实际传输4.34 MB；强制服务器直接返回原始gzip文件时，fetch读取4.34 MB，由应用解压。两者都正常进入可用首帧，不能把前一个8.71 MB当成下载量。

此数值是本机最终构建的资源体积，不是GitHub Pages的公网速度承诺。[公开站点](https://lightyearzh.github.io/slop-wuhan/)已于2026-11-01上线，并完成桌面Chrome加载与基本操作检查；尚未给出公网冷启动的独立计时或流量测量。全部静态部署文件约75 MB，因为其中仍包含可访问的源数据、审计与旧500m分块；它们没有被当前运行入口在首次打开时一起请求。部署记录见[发布说明](PUBLISHING.md)。

## 验证

- 对本轮修改前的整个GEO对象做运行字段规范化后，与WUH1解码结果 `deepStrictEqual`：所有保留字段、来源标签、坐标、孔洞、层级、楼高一致。只有上述不被运行时读取的placement审计属性不再重复传输。
- 普通源建筑23,461栋；渲染部件23,819个；道路连接9,573条；五个专用建筑地标完整保留。地图范围、地形、桥隧与历史立面没有裁掉。
- 111项JavaScript测试、44项Python数据测试、空间审计、生产构建通过。新增测试覆盖精度、中文、整数边界、孔洞、gzip与已解压响应、损坏与截断、包哈希、后台启动让步。
- 真实Chrome：四种方式切换正常；出租车实际前进；黄鹤楼、龟山电视塔、江汉关之间传送保留汽车；无运行错误。
- 注入HTTP503时没有错误地进入ready；显示重试按钮，点击后恢复；直接gzip与自动解压两种托管行为均通过。

证据：[浏览器结果](acceptance/loading-0.8.5/browser.json)、[失败与恢复](acceptance/loading-0.8.5/failure-recovery.json)、[全量字段一致性与体积](acceptance/loading-0.8.5/metrics.json)。本机截图保存在 `output/playwright/wuhan-loading-085.png` 和 `output/playwright/wuhan-loading-085-overview.png`；该输出目录不纳入Git。

复验：`npm run data:runtime` → `npm run verify` → `npm run preview`。完整地理重建 `npm run data:build` 也会自动输出新格式。gzip固定时间戳，输出可重复；无需服务器安装额外解码服务。

## 实际边界

本轮改善首次传输、JS解析负担及加载稳定性，没有把整个城市改成运行时按需流式构建，也没有缩小地图或隐藏建筑。建筑网格生成、场景初始化和着色器编译仍会花时间，设备性能仍会影响进入速度和帧率。上游其他树木、车流和渲染优化可按具体性能瓶颈再单独评估。
