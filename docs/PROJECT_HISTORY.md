## 1. 最初要解决的问题

先用现代武汉验证“城市资料 → 三维场景 → 自由漫游”的完整链路，为后续历史城市提供经验。用户确定武汉后，不再比较其他城市；武汉与汴京保持独立项目。

路线逐步明确为：复用成熟运行系统，保留真实距离与地理骨架，普通建筑批量生成，重要地标专门制作。先把空间、通行和辨识度做好，网约车、任务、轮渡玩法等后置。

## 4. 几次最有价值的纠错

| 用户看到的现象 | 核实后的原因 | 沉淀的规则 |
| --- | --- | --- |
| 建筑稀疏、方盒子多 | 开放轮廓不足；矩形替代丢失形状；用途与高度缺失 | 先补资料和轮廓，属性证据分开记，不能只加随机楼 |
| 换台北后仍不够丰富 | 模块在仓库中，但输入字段、生成器入口和场景挂接不完整 | 检查“源数据→转换→生成→场景→实际画面”全链路 |
| 江面长草、车在地底走 | 整块地形未裁水域；显示三角面与高度查询不一致 | 同一空间依据驱动显示和接触，不能只调车辆Y偏移 |
| 桥中间掉落 | 两条车道各有支撑，中间留出无支撑带 | 验收完整桥宽、变道和双向过渡，不只验中心线 |
| 路边莫名碰撞 | 部分碰撞过宽；有树模型未显示 | 同时查几何、可见性、剔除与碰撞，不一律删碰撞 |
| 城门把道路封死 | 二维建筑外框被当作全高实心体；通道被判成数据冲突 | 显式表达开口和实体高度范围，修四个环节而非只删墙 |
| 高楼多了仍不像武汉 | 模型高度低估、部件丢失、体量和来源年代不一致 | 高度、塔裙分部、轮廓身份和年代要分别核对 |
| 历史街区仍像普通商业楼 | 通用立面不能表达特定建筑构图 | 普通楼用规则，重点楼按身份绑定构件与参考 |
| URL打开像没选角色 | 观景镜头、提示隐藏、滑动高亮及测试状态混杂 | 角色状态、镜头状态、界面状态分别检查；交还普通页面 |

璇宫饭店的早期“5层换算”后来被设计单位“主体6层、28.4m”的资料纠正。旧记录保留当时结论，当前值以新证据和配置为准。类似地，早期关闭的疑似穿楼道路，后续获得明确门洞语义后重新开放；临时处理不是永久地理事实。

## 5. 尚未完成，不能写成已有能力

- 没有逐栋完成全区楼高、用途、立面与年代核准；不少轮廓和高度参考年并不一致。
- 地形仅对两山等局部作显示处理，不是全城精密DEM；桥头坡度、桥隧结构与部分净空仍为估计。
- 程序化地标与历史建筑仍需细化，不是测绘级复原；铭牌是漫游识别辅助。
- 未实现完整轮渡乘船、公交任务或城市生活经济系统；0.9.0新增的汉口短途接送见下文。
- 当前核心区主要整体构建、再按空间和距离剔除。221份旧分块文件存在，不代表已完成按需网络加载/卸载。
- 尚未验证通用城市一键生成、跨引擎无损导出、Blender资产生产线或汴京场景。
- 本机短时帧率、一次截图和自动物理路线，不等同于所有设备性能或完整人工游玩验收。

## 8. 0.9.0：小型出租车接送

参考伦敦任务的分层思路，增加三条约0.8—1.3公里的汉口短途订单。主动接单、道路导航、路边乘客、持续停车、上下车和实际里程结算构成完整循环；普通漫游仍可自由使用。接送判定与乘客显示分开，地图与路面共用一条合法道路路线。

新增6项有实际边界意义的规则测试，JavaScript共117项通过，正式构建通过。三条订单使用原车辆控制器、交通和油门/转向/刹车输入完成浏览器物理验证，没有用传送或强制状态完成订单。录像与素材说明见[出租车说明](TAXI.md)。
