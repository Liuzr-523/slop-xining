# 从武汉实验到北宋汴京：可借鉴的流程与启动交接

整理日期：2026-10-29。性质：经验交接与建议，未启动汴京场景制作、资料采购或引擎迁移。

## 1. 对齐已有汴京计划

工作区已有独立的`bianjing/`仓库。现有[项目定位](../../bianjing/docs/PROJECT_BRIEF.md)、[第一处场景计划](../../bianjing/docs/PHASE1_PLAN.md)、[世界数据最小契约](../../bianjing/docs/WORLD_DATA_CONTRACT.md)和[美术规范](../../bianjing/docs/ART_BIBLE.md)提出：以仁宗朝为时代目标，先做一小段沿河街市，约5—8栋建筑；约50×50m只是初始空间预算，不是已确定的史实或最终尺寸。

这套小样板方向可以保留。武汉证明了持续扩区需要可靠数据和通行约定，也说明大面积通用建筑不自动带来可游览价值。汴京首轮应先验证历史解释、资产质量、连续空间和实际漫游，不先建设完整古城数据库或现代交通系统。

本次不改写汴京已有文档及其未提交工作。本交接文件放在武汉仓库，与[工作记录](PROJECT_HISTORY.md)、[复用流程](CITY_WORKFLOW.md)一起作为下一项任务的输入。

## 2. 武汉方法迁移到汴京，什么改变了

| 方面 | 武汉实验 | 汴京建议 |
| --- | --- | --- |
| 空间底座 | 现代道路、建筑、水域轮廓较明确 | 史料、考古/研究成果、图像测读与显式假设；不把现代开封路网直接当北宋底图 |
| 坐标与尺度 | 现代地理定位，1:1米制 | 保留米制工程约定；无法可靠定位时先用局部坐标，明确尺寸依据和误差 |
| 证据问题 | 高度缺失、轮廓年代不一致、属性不足 | 地点、年代、形制、尺寸和布局都可能不确定，须逐属性标注 |
| 普通建筑 | 大量真实轮廓加程序化立面 | 少量经过审核的成熟资产/构件形成类型，再逐步扩充；不预设每栋都有已知真实平面 |
| 关键地标 | 专门模型提高城市辨识度 | 首轮先做一个有依据且可制作的辨识点；未确定具体历史地标前不把占位名写成结论 |
| 交通与生活 | 汽车、机车、直升机、现代信号和招牌 | 首轮先步行；船、车、摊市和人群按场景需要接入，并另核对时代适配 |
| 通行风险 | 桥、隧道、门洞、坡面 | 河岸、桥头、城门、廊下、院落、狭巷与台阶；继续共用空间依据 |
| 资产互换 | 目前多为Three.js代码和TSL材质 | 世界数据与资产绑定独立；主要资产试验GLB/glTF与Blender，不能假定程序化材质无损导出 |

《清明上河图》等参考与目标时代存在差异，是已有项目规范要求处理的问题；本文件不新增具体历史形制结论。古画也不是可以逐像素照搬的测绘图，应先解释其空间表达和适用范围。

## 3. 历史资料需要比武汉再多一层约束

对每个关键断言分别登记：

- **来源直接支持**：记录原文/图像局部/报告定位，以及它实际支持的内容。来源存在不等于对所有年代、地区都成立。
- **资料测读或换算**：记录从图像、尺寸标注、比例参照推导的过程和误差；不要把测读值写成原文记载。
- **类比推定**：说明采用哪一时期、哪一地区、哪类建筑作类比，为何适用，以及可能不适用之处。
- **美术补全**：补足未记载的背面、装饰、生活物件等；保留可替换性，不让漂亮渲染反过来提高史实等级。

同一栋建筑可以“位置有据、层数待定、屋顶类比、背面补全”。争议方案保留采用理由和备选，而不是只保留最终模型。模板见[证据与资产登记](templates/EVIDENCE_AND_ASSETS.md)。

## 4. 可立即带走的经验

### 4.1 一个稳定的世界实体，允许多种表现

借鉴武汉按ID绑定资料和模型的机制，但换成汴京自己的实体ID。更换某栋店铺的模型时，地点、历史解释、布局和检查路线不应随之消失。模型原点、尺度或包围盒改变则显式更新适配和碰撞。

### 4.2 地面通行先于装饰堆砌

先从同一份数据画二维水陆/占地/孔洞/路线，再搭低成本空间原型。确认河岸不会掉落、桥头能过渡、廊下有净空、院落可按设计进入，之后再用成熟资产替换。铁门关的教训尤其适用于古城门和楼阁：不能把上部屋顶投影挤出成全高实心盒子。

### 4.3 先有代表实例，再抽生成器

武汉的历史外观在绑定具体身份、区分石材/红砖/近代构图后才开始有辨识度。汴京也先选少量符合目标的建筑与构件，完成正面、侧后方和近景审查，再提炼重复的开间、屋面、门面和组合规则。欧式柱式、现代黄鹤楼屋顶和台北寺庙资产都不能仅改名字便当作宋代建筑。

### 4.4 保留混合资产路线

已有汴京计划允许成熟模型、人工修改、专业AI和程序化并用。武汉的成功不构成“汴京所有模型必须由代码生成”的理由。选择方式时比较具体质量、历史适配、授权记录、修改量和复用成本；没有实测人工基线时不宣称节省了多少工时。

### 4.5 必须看运行中的完整链路

文件导入、测试通过、模型生成、加入场景、实际可见、碰撞符合、路线能走，是不同结果。样板要检查加载失败、资源缺失、背面空壳、材质不一致和看不见的碰撞。固定摄影机与普通漫游都要验收，截图不能代替走通。

## 5. 建议带入首轮的复用矩阵

| 分类 | 候选能力 | 首轮处理 |
| --- | --- | --- |
| 保留方法 | 固定米制框架、稳定ID、属性证据、基线提交、阶段验收 | 直接写入场景约定与交付模板 |
| 小范围接入验证 | 输入、步行相机、加载状态、光照时段、截图接口 | 先验证一个可运行最小场景，再决定采用哪些武汉/上游模块 |
| 适配后复用 | 多边形/院落、通道高度范围、共享地面接触、沿线排布、资产占地检查 | 换成汴京类型和数据，加入河岸、廊下、桥头的反例测试 |
| 保留思路、重做形制 | 屋顶、梁柱、门窗、地标构件、地面材质 | 必须经过历史和近景审核，不沿用欧式或现代建筑外形 |
| 调查后再定 | GLB/glTF接入、Blender复用、资产库和AI工具 | 武汉尚未验证完整资产交换链，不能标为现成能力 |
| 首轮暂缓 | 汽车、过江隧道、现代交通信号、网约车任务、全城流式加载 | 不为小样板先移植；后续出现明确需求再评估 |

这份矩阵是建议，不替代既有“最小运行测试后选型”的安排，也未决定最终游戏引擎。

## 6. 下一项任务可以直接按这六步启动

| 步骤 | 要做的具体事 | 完成条件 |
| --- | --- | --- |
| 1. 定义一段场景 | 在既定时代目标下选择具体沿河局部、参考资料、辨识点和步行路线 | 形成`SCENE_BRIEF.md`；地点和尺寸有依据或明确为假设 |
| 2. 调查必要资产 | 检查建筑、屋顶/门面、桥岸或码头、船与摊位等实际候选 | 形成`ASSET_SURVEY.md`和`SCENE_FEASIBILITY.md`，有可启动候选及具体缺口；不要求穷尽平台 |
| 3. 做最小空间原型 | 同一世界数据输出二维检查图与三维地面、河岸、体块、开口 | 出生点到辨识点的路线能走；错误可定位到实体 |
| 4. 换入少量合格资产 | 统一米制、朝向、原点、材质，保留来源与转换；扩成5—8栋连续场景 | 近景与侧后方可看，至少替换一个资产而不破坏实体和路线 |
| 5. 完整样板验收 | 主视角、近景、布局、侧后方、临水和狭巷检查；记录目标设备运行表现 | 历史解释、视觉、通行和运行分别给结论；有可复查图像和实际路线 |
| 6. 复用交付 | 保存原始可编辑资产、布局、证据、处理步骤、检查和基线 | 主要资产完成实际交换格式/Blender检查；未保留能力明确列出 |

前两步已有计划但尚未完成；本轮只整理武汉经验，不把它们记成已执行。阶段验收应沿用已有汴京规范，并将武汉暴露的“孔洞、河岸、隐藏碰撞、模型替换、截图状态”加入检查。

## 7. 首轮建议检查表

- [ ] 目标时代、资料年代及类比/补全分开，关键位置和尺寸的未知项可见。
- [ ] 水陆、道路、占地与开口来自同一份世界数据；没有装饰物封住主路线。
- [ ] 模型大小和正面方向正确，正面、背面、侧面都可近看。
- [ ] 河岸边界、桥头过渡、门洞净空、院落和狭巷有实际通行检查。
- [ ] 一个成熟资产换成另一个后，实体ID、历史证据和布局仍可用。
- [ ] 资产入库信息包括实际文件、来源与授权核验、修改记录、碰撞代理。
- [ ] 运行错误和缺资源能明确暴露，不把残缺加载当成完成。
- [ ] 固定机位条件可重复；交还的是正常漫游状态。
- [ ] 主要资产的跨工具检查真的做过，程序化材质的不可移植部分有记录。
- [ ] 未测项、剩余问题、可回退基线及下一轮最小任务写清楚。
