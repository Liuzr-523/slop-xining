# 从城市数据到可游览街景

本项目采用“真实地理骨架 + 程序化通用建筑与街具 + 专门制作的地标”路线。不是逐栋人工摆放，也不是把地图截图直接变成三维世界。

## 武汉当前如何生成

1. **原始资料**：湖北 OSM PBF 提供道路、水面、绿地和部分建筑；固定版本的 Overture 补充建筑轮廓。原始提取、来源和哈希保留。
2. **统一空间**：投影到同一个以米计的局部坐标；保留 OSM 节点、道路层级和对象 ID。原点固定，扩区时不移动已有城市。
3. **合并与清洗**：组装建筑和水域内外环；优先 OSM、去除 Overture 重复项；区分真实高度、层数换算及视觉估算。
4. **空间规则**：用真实建筑轮廓裁剪估算路面；将未经确认的穿楼地面通道关闭在生成层，并记录来源 ID。桥隧不当成平地道路接入。
5. **普通建筑**：按原始平面轮廓拉升；通用材质生成窗、墙面等细节；轮廓同时用于碰撞。外墙样式和多数楼高仍不是实景资料。
6. **街具**：沿道路产生候选位置；统一检查建筑、水面、所有相交道路、步行通道与其他街具，合格后才生成路灯、树池、座椅和矮柱。按完整占地半径检查，不只检查中心点。
7. **地标**：单独编写或接入特色模型，按数据定位。江汉关为代码生成的专用外观模型，比例来自 OSM 平面和公开实景参考，不是通用建筑随机碰巧生成。
8. **输出与验证**：500m 分块、地图目的地、碰撞、来源与审计报告；浏览器复用上海的角色、相机和车辆系统。

## 上游是否也是这套思路

查看当前本地上游快照后：

- **Slop New York**：通用规则批量生成城市表现，同时读取真实地理资料，并用专门代码制作标志性建筑。其建筑构建脚本读取 NYC Open Data 建筑轮廓、`height_roof` 与年代等属性；道路还使用 NYC 的中心线资料，OSM 提供部分公园、水岸等要素。其优势也来自当地资料，并非仅凭 OSM 就能得到同等精度。
- **上海改编**：复用纽约的渲染和操控，接入 OSM/PBF；核心地标单独制作。外围还包含明确标记的、按种子生成的补充建筑，制造更完整的沿街空间。
- **武汉**：继续复用上海引擎，普通建筑优先保留 OSM/Overture 真实轮廓。目前没有用凭空补楼的方式伪装数据覆盖，因而数据不足仍能被明确看出来。

对应源码：`../reference-slop-newyork/tools/build-buildings.py`、`../reference-slop-newyork/tools/build-geodata.mjs`、`../reference-slop-newyork/js/landmarks.js`、`../reference-shanghai/tools/build-citywide.py`。

## 如何扩区

区域入口已集中到 `config/wuhan-pilot.json`，导入器与生成器共同读取。可复制区域配置、扩大 bounds，再用：

```sh
npm run data:build -- --profile config/your-area.json
npm run verify
```

当前配置仍要求固定武汉原点和 500m 分块；地标/目的地逻辑仍围绕现有汉口样板，**尚不是任意城市的一键转换器**。扩展区域必须包含现有江汉关样板，或者另行配置地标与目的地适配。湖北 PBF 可继续复用，Overture 小范围文件需要先重新提取到覆盖新范围；若提取范围不足，生成器会停止并提示，不会把空白区域当作完成。

下一步扩展应依次补齐区域配置、来源快照、自动报告和固定验收路线，而不是在整个武汉手动修建筑。江汉关式地标可以逐个作为可复用资产接入，普通街区则由规则批量生产。

## 检查入口与边界

- `npm run data:build`：导入、生成，空间冲突门禁不通过则不替换已有城市数据。
- `npm run audit:data`：从已生成文件独立复查路面/建筑相交及道路中心线穿楼。
- `npm run verify`：运行通用与空间规则测试、生成数据审计及生产构建。
- `public/data/spatial-audit.json`：关闭的疑似穿楼段、来源 ID、路面裁剪面积与剩余冲突。
- 浏览器 `window.wuhan.city.placement.audit()`：本次实际生成街具的接受、拒绝原因与剩余规则冲突。

这些检查针对当前生成的地面几何与规则占地，不意味着城市已达到实测精度。关闭的通道需要后续确认是否为门洞、院内车道、屋檐下通行或标注错误，不能把临时关闭当作真实道路不存在的结论。
