# 出租车原型审阅与本次视频的取舍

审阅日期：2026-11-01。对象为工作区未提交的`js/runtime/taxi-fare.js`、`main.js`接线、`tools/video-shots-taxi.mjs`，以及X01—X03三个录制片段。此次只审阅，不修改或发布他人的实现。

> 后续：用户已批准实施，0.9.0实现与验证记录见[出租车说明](TAXI.md)。本文保留实施前的审阅结论。

## 建议

值得在这次视频所对应的新版本中加入轻量接送任务，让自由漫游有一个明确目的；当前原型可保留为流程底稿，不能直接作为完整可玩的出租车机制上线。保留已公开的0.8.5作为基线，任务功能单独验证后发布，再录实际行驶的一单。视频制作可继续，不必等待完整网约车经营系统。

## 已核对的内容

- 原型具有候客、接客、送达、结算、跳过及虚拟收入状态，还有光柱、车顶方向箭头和任务卡。
- 三段视频共20秒。逐段抽查画面，并核对录制轨迹：车辆位置不变、速度均为0。录制脚本通过隐藏测试按钮调用`newFare`、`startRide`、`endRide(true)`切换状态，没有实际接客和送客驾驶。它是状态流程演示，不能当作真实跑通一单的证明。
- 原型随机选道路节点，以水平直线距离筛选接送点，并据直线距离估计时间、车费；没有计算道路可达性或导航路线。
- 到达检查是水平距离小于18m、速度小于5m/s（约18km/h），没有持续停车或高度层检查。位于桥上、桥下或隧道上下重合位置时存在误判风险。
- 工作区`main.js`已无条件创建任务模块，普通汽车漫游也会自动候客；`taxi-demo`参数仅控制隐藏测试按钮，不是玩法总开关。该状态尚未提交，不能把它说成公开版已有功能。
- 传送、切换其他方式、任务期间暂停及重进页面尚无完整规则；收入只是本次会话状态。未找到该模块的专用规则测试或真实行驶验收。

## 对照伦敦参考

本机`reference-london-loop`基线`3c7525e`与审阅时远端main一致。`js/rideldn.js`已提供道路图`RoadGraph`、路线显示`RouteRibbon`、候车人`PassengerFigure`、停车停留、上下车过程，以及计费和传送识别等逻辑。订单会计算实际路线路径及预计行程，不只是随机两点加直线箭头。

可以复用其路由、停靠状态机和乘客表现方法，但不能整文件替换进武汉：道路字段、原点、靠右通行、桥隧高程、地图接口、控制器和它依赖的backend都需适配。当前原型并没有接入这几个核心模块。

## 本轮最小可交付范围

1. **主动开始**：保留自由漫游，点击“开始接单”才进入任务；可取消或结束，不在打开页面后强制接活。
2. **少量可靠订单**：先选汉口3—5条实际可通行路线，使用有名字的地点，约2—4分钟一单。上下客点是附近可停车路边，避开江汉路步行面和地标台阶；先不加入随机跨江订单。
3. **能看懂怎么走**：地图标出乘客、目的地与沿道路的路线；显示实际路线剩余距离，方向提示随路线转弯。不能只用穿楼、过江的直指箭头。
4. **有乘客与停靠反馈**：复用现有人物系统做候车人及简化上下车。车辆到正确路边、正确高程且停稳一段时间后，才切换接送状态；有清楚的文字或短音效。
5. **实际行程结算**：按真实行驶距离和时间计算虚拟车费。先给预计时长，不必强制很紧的倒计时；取消、切换方式、传送必须有规则，不能传送刷单或隔层完成。

暂缓账号、服务器、排行榜、复杂评分、品牌化网约车界面、完整经营系统及全城随机派单。先完成一个能持续玩、也能清楚演示的接送循环，之后再扩展桥隧跨江订单。

## 验证与录制

至少跑完三条不同路线，并验证正确停靠、擦边驶过不接客、取消/超时状态、模式切换和传送不能误完成，以及地图路线与实际可通行道路一致。任务状态与路线选择应有独立测试，录制使用普通玩家流程，不调用强制上车或完成按钮。

最终素材录一次真实的“接单→驶往乘客→停车上车→沿路送达→结算”，保留完整原片，再剪约25—40秒用于视频。与当前站位不动、任务文字切换的演示区分。原视频脚本的“后续想尝试接单”段，只有在此功能实测、发布后才改成已有玩法；此前继续使用原来的未来设想表述。

这次提升的重点是玩家能完成一次接送，而非仅把任务卡变漂亮。它也能回应大地图中“开过去做什么”的问题，又不必扩大地图或同时开发完整开放世界经济。
