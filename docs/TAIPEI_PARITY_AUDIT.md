# 台北运行效果链路复查 · 0.4.1

2026-10-28。以武汉 `537275c`（0.4.0）为修复前基准，对照本地 `reference-taipei`、revision `1d70708fc92a088b779c8c0e22677adb64966a1b`。本轮重点是把已经存在的功能实际接通，不改高度推断规则，不扩大区域。

## 结论

上一版迁移了主要渲染模块，但部分数据契约与特有街具没有接完整。不能把迁移完成理解为已经呈现了台北的完整丰富度。发现并修复五类问题：

| 链路 | 0.4.0 的实际情况 | 0.4.1 处理 |
| --- | --- | --- |
| 道路曲线与路口 | 每个形状折点变成节点，2,111 条连接中 1,193 条短于 20m；所有节点都有路口半径。原版沿路灯、树木、车道线会按长度和端部距离筛选，因此大量短段受到影响；车辆也要在无路口的普通弯点做连接转向 | 只在 OSM way 端点、共享源节点和真实信号节点处分段，弯点留在折线中；1,039 条连接、409 条有中间形状点，普通度二弯点半径为 0。保留源 node ID、方向和步行禁车，不吸附附近不相交道路 |
| 信号灯 | `signals=[]`，原导入器在节点阶段只保留商店等 POI，丢掉 highway 设施 | 重新从同一个现有湖北 PBF 读取 26 个 traffic_signals 节点，形成 17 组控制器；实际可放置并渲染 43 组信号头。节点来源保留，二相配时来自原版规则，是视觉估计，不是武汉实时时相 |
| 招牌语义与形态 | 只取建筑首层边线，未传完整 POI；统一 shop 类别，竖牌条件写死 false。实际 0 竖牌、212 横牌、图集 12 个源名称 | 接入源 POI 的银行、餐饮、咖啡、商店、旅馆等类别；楼内关联与 22m 内近墙估计分别标记。按横牌、竖牌实际占地检查建筑、水面、机动车道和步行中部；实际 119 竖牌、85 横牌，图集 32 个源名称 |
| 屋顶体量 | 原先新增的避让规则检测贴着包围框边缘的候选，点落在边界上被判为不在面内；1,584 个屋顶候选最后只得到 5 个屋顶房，剩下主要是水箱 | 候选先内缩，再在原屋顶内缩放、平移搜索；检查完整檐口、凹轮廓和院落，不仅查四个角；生成 836 个示意屋顶房，水箱 2,222 个。限制坡屋顶高度，避免大跨度房体产生过高尖顶 |
| 武汉特色街具 | `wuhan-streetscape.js` 仍在仓库，但新入口未调用；原江汉路树池、座椅和特色灯从场景消失 | 接回已有模块、转换 y=2 到 y=0 的地面接口，使用同一空间检查。恢复 9 株树池树、13 盏特色灯、11 张座椅、69 个矮柱；树池采用台北详细树木生成器，避免混用原低多边形树冠 |

以上数量均为程序生成记录，不是实测设施清单。招牌总数略降，是完整占地、短墙和近邻去重后的结果，不以数量增加代替正确布置。

## 确认已经应用的台北能力

逐项阅读并比较：

- `js/buildings.js`、`js/tsl-materials.js`：墙面分格、瓷砖、铁窗、空调、封闭阳台、首层店面、室内假深度、夜间发光，以及屋顶房／水箱。当前武汉材质主体与台北相同，已处理简体文字和地名；本轮增加正面／背面墙和样式统计，避免只凭模块文件存在判断功能启用。
- `js/lighting.js`、`js/post-processing.js`、`main.js` 的渲染管线：物理天空、环境光、太阳阴影、SSR 反射、Bloom 和时段预设已经使用。比较排除繁简和命名变化后，光照预设只有名称差异，后期模块一致。没有发现一个被漏开的“高画质开关”。
- `js/trees.js`：细叶片、树干、树种变体和距离分级代码一致，确已被 `createTreeField` 调用。街边能种多少还取决于人行道、墙面、交叉道路和设施占地。
- `js/traffic.js`、`road-paint.js`、`street-props.js`：车道图、跟车、连接曲线、信号停车、路面标线、信号灯、树木、招牌、停车都在运行路径中。武汉交通密度此前已做适度降低；本轮不将台北的机车密度直接套到武汉。
- 相机、地图和场景距离裁剪均已接入。台北特定地理、远山与专用地标有意替换，不是遗漏加载。

实际普通建筑样式统计：walkup 1,252、midrise 767、glass 6、civic 74。说明玻璃大楼少主要受目前已知用途与高度触发条件限制，材质功能本身并未缺失。42 栋历史分类仍采用通用公建立面，需要后续单独建立汉口历史建筑样式，不能称为已复原。

## 仍然存在的差距

1. **楼高和用途不足**：2,081 栋缺高，显示层仍按同一套 Hankou v1 规则推断。没有因为查漏就任意提高楼高。真实层数、塔楼分部和年代资料仍是天际线质量的核心约束。
2. **范围与远景**：武汉当前约 2×2km；台北覆盖约 9×8km，并带盆地外围山体。武汉区域外仍有裁剪边缘和空白，当前没有延伸远景建筑层。台北山体不能移作武汉地形。
3. **地标资源**：台北有 15 个专用地标配置和共享宫殿屋顶生成器；武汉当前只有江汉关达到专用模型层级。两个宗教建筑源记录是荣光堂与汉口圣母无原罪堂（church），不能套用原版寺庙燕尾屋顶来增加数量。
4. **缺少的源图层**：这个 PBF 试验范围中读到 26 个信号节点，但没有 highway=crossing 节点，因此本轮 `crossings` 仍为 0。没有把推测横道当成真实点位。地铁、桥隧、DEM、广场、草地与林地的精细分类还需相应适配和核查。
5. **区域风格**：台北的通用空调、窗格、彩色外墙、屋顶设备提高丰富度，但并不自动成为汉口实景。江汉路重点建筑、商业首层和沿江历史建筑还需要参考资料校准。

## 可复现入口与验证

- `npm run data:build`：重新导入 OSM，构建武汉源层，接着运行新转换。
- `tools/runtime_streets.py`：真实节点图、弯道形状、路口半径、信号与过街资料关联。
- `tools/runtime_signs.py`：POI 类别、源名称、关联置信度、完整牌体平面避让。
- `js/runtime/roof-layout.js`：含院落和凹口的屋顶放置规则。
- `window.wuhan.stats` 与 `window.wuhan.placement.audit()`：浏览器实际生成统计与剩余空间规则冲突。
- `public/data/runtime-audit.json`：图层数量、来源、推断口径和拒绝原因。

57 项 JavaScript 测试、17 项 Python 测试、源层空间审计与构建通过；新增用例验证弯点保留、共享节点连接、近邻不误连、无源不生成信号／横道、POI 类别与关联、屋顶檐口及内院。浏览器运行错误 0、当前规则内街具冲突 0；一个短样本 p50 约 16.7ms、p95 约 19.2ms，预编译和移动到新视角仍可能有瞬时停顿。不是全城或所有设备的性能保证。
